# ICMP 隧道：1:1 长轮询（Pull）传输方案设计规格

> 本文档描述**目标方案本身**，不引用现有实现。实现细节（代码结构、类名、现有常量）不属于本规格，
> 落地时按本规格重新组织。

---

## 1. 设计目标与约束

### 1.1 目标

在 ICMP echo 之上提供**可靠、有序、双向**的字节流，供隧道转发 TCP/UDP 流量。

### 1.2 环境约束（决定架构）

| 约束 | 后果 |
| --- | --- |
| ICMP 无连接、无端口、无会话 | 必须自建 session 标识与状态 |
| 存在 NAT / 有状态防火墙 | **服务端不能主动向客户端发包**：未关联请求的回程包会被丢弃 |
| 可能丢包、乱序、重复 | 需要序号、确认、重传、去重 |
| 单包有效载荷小（受 MTU 限制） | 需要分片与重组 |
| echo reply 必须回显 request 的 `ident/seq` | 回包身份由请求决定，服务端没有自由选择权 |

**最核心的一条**：因为服务端不能主动发包，且回包身份必须回显请求身份 ——
所以**下行数据只能"搭"客户端请求的回包顺风车**。这就是长轮询（pull）模型的由来。

---

## 2. 核心模型

### 2.1 基本契约

1. **客户端发出的每一个包都是一个"请求"**，携带自己的 ICMP 身份 `(ident, seq)`；
2. **服务端必须对每个请求恰好回一个包**，且回包**回显该请求的 `(ident, seq)`**；
3. 回包内容二选一：
   - 有下行数据 → 携带一个下行分片（`DATA`）+ 累计确认；
   - 等待窗口耗尽仍无数据 → 携带空载荷的纯确认（`ACK`）；
4. **服务端从不主动发起新请求**，只在收到请求时回应（控制类消息如 RESET 除外）；
5. **所有重传由客户端驱动**：客户端为每个在途请求计时，超时未收到回包就重发。

> 契约 3 是可靠性的根基：**请求不会"挂着不回"**，因此客户端的超时判定永远有明确语义
> （要么回包到了，要么回包丢了）。

### 2.2 为什么不是"服务端主动推"

若服务端在收到下行数据时立即向客户端发 echo，该包没有对应的 request，
NAT 会话可能不存在 → 丢弃；即便到达，客户端也无法把它与任何在途请求关联。
因此下行必须等待客户端下一次请求。

## 3. 报文格式

### 3.1 ICMP 层

- 客户端 → 服务端：`ECHO_REQUEST`，`ident` / `seq` 由客户端分配；
- 服务端 → 客户端：`ECHO_REPLY`，`ident` / `seq` **必须等于请求的 `ident` / `seq`**。

`seq` 是**请求的唯一匹配键**（同一 session 内），客户端据此把回包路由到对应在途请求。

### 3.2 传输层包头（ICMP payload）

| 字段 | 说明 |
| --- | --- |
| `magic` + `version` | 协议标识与版本，用于版本协商与非法包过滤 |
| `session_id` | 复用一条 ICMP 通道上的多条逻辑流 |
| `msg_seq` | 本方向的**分片序号**（单调递增，回绕），一个分片一个序号，用于去重与按序重组（见 3.3） |
| `ack` | 对向的**累计确认**（已收到的最大连续 `msg_seq`） |
| `op` | `DATA` / `ACK` / `PING` / `CONNECT` / `CLOSE` / `RESET` ... |
| `payload` | 有效载荷 |

每个方向独立编号：`msg_seq` 是"我发给你的第几条消息"，`ack` 是"我收到你的第几条"。

### 3.3 分片与重组

#### 3.3.1 分片规则：按字节流切，不按消息切

上层是**字节流**（隧道转发的 TCP），没有天然消息边界。因此采用与 TCP 一致的策略：
把字节流按 `MSS` 切成**定长分片**，每片独立编号、独立确认、独立重传。

- **一个 `msg_seq` 对应一个分片**（不是一条上层消息）；
- 因为一个 ICMP 包只能承载一个分片（2.1 契约 3：回包二选一），
  所以 `msg_seq` 同时也是"第几个 ICMP 数据包"，与传输层一比一对应；
- 分片大小固定为 `MSS`（末片可短），接收端按 `msg_seq × MSS` 即可定位，
  **无需额外传偏移量**。

> 这与"按消息切分"的区别很关键：若按消息切分，一条大消息跨越多个分片时，
> 必须额外传 `(msg_id, frag_index, frag_count)`，且确认要按消息整体确认、
> 无法做选择性重传。按字节流切则天然支持逐片确认与乱序重组。

#### 3.3.2 `MSS` 的确定

```
MSS = PathMTU - IP头(20, IPv4) - ICMP头(8) - 传输层包头 - 上层包头
```

要点：

- 必须扣除**所有**封装开销，只把剩余部分用于载荷；
- 保守取值可默认 `MTU=1500`，但移动网络（含隧道叠隧道、PPPoE）可能更小，
  应支持探测或由 CONNECT 协商；
- `MSS` 一旦协商，**两端必须一致**，否则接收端按 `msg_seq × MSS` 定位会错位；
- 服务端在 CONNECT 中回显最终生效的 `MSS`，双方以该值为准。

#### 3.3.3 分片元数据

分片信息**不需要额外字段**，完全由 `msg_seq` + `MSS` 隐含表达：

| 信息 | 表达方式 |
| --- | --- |
| 分片是否完整 | 载荷长度 `== MSS` 则完整，`< MSS` 即末片 |
| 分片在本方向的位置 | `msg_seq`（单调递增，首片为 1） |
| 该片是否已收到 | 累计 `ack` 推进；可另用位图表达乱序已收 |

流结束（FIN）仅表达在 `op` 层，不占用 `msg_seq`，以免污染数据序号空间。

#### 3.3.4 接收端重组

```
缓冲区: 按 msg_seq 索引的已收分片，以及 expected（下一个待交付序号）

收到分片 msg_seq = n:
    if n < expected:        丢弃（重复）
    if n > expected:        缓存（乱序），并发送累计 ack 触发对端补洞
    if n == expected:       交付，expected += 1
                            然后向后续连续缓存的分片推进并一并交付

缺口处理:
    若 n 长期 > expected（缺口未补齐），不能干等 ——
    通过 ack 落后触发对端 pull 驱动重传（5.4），
    或由本端在回包中重复携带旧 ack 触发快速重传
```

要点：

- **重复分片必须丢弃**（网络会重复投递），否则上层收到重复字节；
- **乱序分片先缓存**，不因乱序就丢弃重传（否则浪费带宽）；
- **重组缓冲区必须有上限**：超出上限时拒绝超前分片并强制对端按 ack 回退，
  防止恶意/异常对端用超前序号撑爆内存（与 6.1 的 pending 上限呼应）；
- **重传的粒度是单分片**：因为每片独立编号，补洞只需重传缺口那一片，
  而非整条消息 —— 这正是 3.3.1 选择字节流分片的原因；
- **ack 的携带义务**：接收方依赖"有反向流量"才能把 ack 传出去（见 5.4.1）。
  因此**空闲时也必须发空 pull**（4.2 / 7.5）—— 它不只是保活，还承担着
  "把累计 ack 送出去"的职责。若两端同时静默，会因为 ack 传不出去而误触发对端重传。

#### 3.3.5 分片大小与重传的相互影响

- 片越小 → 丢包时重传代价越小、但协议开销占比越高、同样带宽需要更多包
  （而 ICMP 包数受限于窗口与限速，见 6.1），故 `MSS` 不宜过小；
- 片越大 → 单包丢失影响面越大，且越易触碰路径 MTU 上限被分片/丢弃；
- **建议 `MSS` 取到协商 MTU 允许的最大值**，让每包承载尽可能多数据，
  这与"小窗口 + 低包数"的定位一致。

### 4.1 状态

| 结构 | 键 | 内容 | 用途 |
| --- | --- | --- | --- |
| 发送缓冲 | `msg_seq` | 待发/已发未确认分片 | 重传与按序交付 |
| 在途请求表 | `icmp_seq` | `(msg_seq, payload, 发出时刻, 重试次数)` | 超时重传、回包匹配 |
| 已交付集合 | `icmp_seq` | 已收到回包的请求 | 丢弃重复/迟到回包 |

### 4.2 拉取循环（常驻）

**必须始终维持 ≥1 个在途请求**，否则下行数据无法送达（会被阻塞到下一次请求）。

```
loop:
    if 存在可发送内容（待发数据 / 需要携带 ack / 保活）and 在途数 < cwnd:
        icmp_seq = 新序号
        pkt = build(msg_seq=..., ack=对向累计确认, payload=一片或空)
        在途表[icmp_seq] = (pkt, now, 0)
        send(pkt)
    else:
        # 在途已满或无事可做：等待回包或超时
        await 任一在途请求回包 / 超时
```

要点：

- 在途上限由**动态窗口 `cwnd`** 控制，而非固定常量：空闲为 1，有数据传输时爬升，
  上限 `WINDOW_MAX=5`（完整策略见 6.1）；
- 拉取间隔应**远小于等待窗口**，理想情况是"收到回包后立刻补发下一个请求"，
  使在途数尽快爬满 `cwnd`；
- 无事可做时也要发**空 pull**（只带 `ack`），既取下行数据又兼作 NAT 保活。

### 4.3 per-request 超时重传

```
on 请求 icmp_seq 在 T 秒内未收到回包:
    if 重试次数 < MAX_RETRY:
        用【相同 msg_seq】+【新 icmp_seq】重发
        重置计时
    else:
        判定链路失效，触发 RESET / 重连
```

**关键：重传换 `icmp_seq`、保持 `msg_seq`。**

- 换 `icmp_seq`：让重传包成为一个**新的、可被匹配**的请求，其回包不会与旧请求的回包混淆；
- 保持 `msg_seq`：让服务端能识别"这是同一条消息的重传"，从而幂等处理（见 5.2）。

### 4.4 回包处理

```
on 收到 reply(ident, seq):
    if seq 不在在途表: 丢弃          # 迟到/重复的旧回包
    if seq 已在已交付集合: 丢弃
    标记 delivered；从在途表移除
    处理 ack（释放发送缓冲中已确认的分片）
    若有 payload: 按 msg_seq 顺序交付给上层（乱序则缓存等待补洞）
    按 4.2 立即补足新的在途请求
```

## 5. 服务端设计

### 5.1 状态

| 结构 | 键 | 内容 | 用途 |
| --- | --- | --- | --- |
| 待回应请求表（pending slots） | `icmp_seq` | `(ident, seq, msg_seq, ack, 到达时刻)` | 派发的唯一数据源 |
| 下行队列 | FIFO | 待发分片 | 承载上层写入 |
| 下行已发未确认缓冲 | `msg_seq` | 已发出的分片 | pull 驱动重传 |
| 已处理请求表 | 上行 `msg_seq` | 最近一次回应内容 | 上行重传幂等（见 5.2） |

### 5.2 上行请求的幂等处理

**幂等只针对上行方向**：客户端重传时保持 `msg_seq` 不变，服务端若把重传当成
"新请求"重新处理，会**重复执行副作用**（例如重复向上游转发同一段数据）。

因此服务端记录"已处理过的上行 `msg_seq` → 上次的回应结果"（TTL 建议 60s），
重传命中时**跳过副作用、直接回应**：

```
on 请求(上行 msg_seq = m):
    if m 已在已处理请求表中:
        # 幂等：不重复执行副作用（不再向上游转发）
        用【当前请求的 ident/seq】重发上次的回应
        return
    else:
        执行副作用（向 pending 表登记 / 向上游转发载荷）
        记录 m → 本次回应
```

注意：**重放要用新请求的身份**，而不是当初那个回包的身份（旧身份已失效）。

> ⚠️ **这里有一个必须避开的陷阱**：幂等表**只能按上行 `msg_seq` 索引，
> 绝不能按"下行分片序号"索引，也不能用它来决定"回哪个下行分片"**。
> 上行 `msg_seq`（客户端第几片数据）与下行分片序号是**两个独立序号空间**，
> 二者在重传时会打架。详见 5.6。

### 5.3 统一派发器 `dispatch_loop`

派发是服务端的**唯一发送出口**。由它独占操作 pending 表，可彻底消除并发竞态。

```
W = T - margin            # 等待窗口，margin 建议 0.5s
Δ = 派发扫描间隔           # 必须 < margin，建议 0.05~0.1s

loop:
    await (下行队列非空事件) 超时 Δ
    for slot in 待回应请求表:
        # 1) 上行幂等：该请求是重传且已处理过 → 原样回应，不重复副作用
        if slot 是重传 and slot.msg_seq 命中已处理请求表:
            用 slot 身份重发上次的回应
        # 2) 补洞优先：存在 RTO 过期的未确认下行分片 → 先补最早那一片
        elif 存在 RTO 过期的未确认分片:
            取【最早未确认】的那一片，用 slot 身份发出
        # 3) 发新数据：下行队列有待发分片 → 发队首
        elif 下行队列非空:
            取队首分片，用 slot 身份发出（DATA + ack）
        # 4) 无数据可发 → 等待窗口耗尽后回纯 ACK
        elif now - slot.到达时刻 >= W:
            用 slot 身份发纯 ACK
        else:
            继续等待
        # 上述任一分支执行后，该 slot 从表中移除
```

> **分支顺序即优先级**：幂等 > 补洞 > 新数据 > 纯 ACK。
> 特别是"补洞优先于发新数据"（见 5.4.4），若实现时写成"取下行队列队首"，
> 缺口会被新数据持续插队，导致对端**整体交付永久停滞**。

设计要点：

- **事件唤醒 + 周期扫描**：下行数据到达立即发送（零延迟），同时每 `Δ` 兜底扫描超时 ACK；
- **单一所有者**：只有 `dispatch_loop` 触碰 pending 表与下行队列，无需加锁；
- **每个 slot 出口必带一个回包**，契约 2.1-3 成立；
- **`Δ < margin` 是硬约束**：否则最坏情况 ACK 在 `W + Δ` 才发出，若 `Δ ≥ margin` 就超过客户端
  超时 `T`，会被误判为丢包而触发无谓重传；
- **pending 上限作为兜底**：异常客户端疯狂请求时应 RESET，避免内存被 pending 表吃爆。

### 5.4 下行确认与重传：pull 驱动

#### 5.4.1 服务端凭什么知道"客户端收到了"

服务端**只在收到请求时才知道对端的进展**，且这个信息完全来自请求包里的 `ack` 字段：

- 服务端把一个分片塞进某个请求的回包 → 该 slot 出表 → 服务端只知道"**已发出**"，
  并不知道客户端是否收到；
- 客户端收下分片 n，在下一次上行请求中携带 `ack = n`；
- 服务端收到该请求，`ack = n` 即表示"**对端已连续收到第 n 片**"。

因此：

- **确认必须由数据接收方在反向流量中携带**，承载位置就是报文头的 `ack` 字段，
  每个上行请求顺便捎带，无需额外报文；
- 上行若长期无数据，客户端仍要持续发空 pull（4.2），否则其 ack 传不上去，
  服务端会误判下行分片未被确认而反复重传；
- **ack 是累积且单调不减的**，天然抗重复、抗乱序：新到的 ack 覆盖旧 ack，
  落后的 ack 不会让已释放的分片"复活"。

#### 5.4.2 释放 vs. 触发重传

两件事必须分开，否则会把"ack 还在路上"误判为"分片丢了"：

```
on 新请求 slot 到达:
    ① 用 slot.ack 释放下行缓冲中 msg_seq <= ack 的分片
       （已确认，安全移除；ack 单调不减，无需撤销）

    ② 检查剩余未确认分片中，是否存在【发出时刻 + RTO 已过期】的
       if 存在:
           取最早未确认的那一片，用【当前 slot 的身份】重发
           更新其发出时刻
       else:
           （ack 落后可能只是回程延迟，继续等待，不重发）
```

**为什么 ② 要带超时判定，而不能只看 `ack < 已发最大号`**：
若一发现 ack 落后就重发，会把"数据已收到、但 ack 包还在路上"的分片白白重发一遍，
在 RTT 较大时会造成大量无谓重传。因此必须给未确认分片记发出时刻，
只有**超过 RTO 仍未被 ack 覆盖**才判定为丢失。

这个 RTO 的语义与客户端的 per-request 超时 `T` 呼应，建议取同一量级
（见参数表），使"下行分片丢了"与"上行请求丢失"的检测时延一致。

#### 5.4.3 重传天然换信封

重传由**当前请求**触发，因此重传包绑定当前请求的 `(ident, seq)`，
是一个合法的、可被客户端匹配的回包，不存在"用旧身份重发导致无法匹配"的问题。

> 推论：下行分片**不应进入"超时自动重传"队列**。若让它带定时器重发，
> 由于回包身份必须回显请求身份，那个重发包必然沿用旧的 `(ident, seq)` ——
> 客户端要么因去重而丢弃它（分片永久丢失），要么重复交付（数据重复）。
> **两种结果都错。** 因此服务端的重传只能由 pull 驱动。

#### 5.4.4 一个请求只能带走一个分片时的补洞效率

若发生缺口（如丢了第 5 片、已发到第 9 片），重传逻辑每次请求只补一片。
在 `WINDOW_MAX=5` 下，缺口会在少数几个 RTT 内被补齐，
但**必须保证"补洞优先于发新数据"**，否则新数据持续发出会让缺口永远排在队尾：

- 下行缓冲中的分片按 `msg_seq` 有序；
- 派发时**优先取最早未确认的分片**，而不是简单取队首新分片；
- 等价于"重传优先级高于新数据"，避免缺口导致的整体交付停滞（队头阻塞）。

#### 5.4.5 关于"误判重传"：延迟 vs. 丢失的不可区分性

**任何基于超时的重传都会误判**：第 1 片只是比第 2 片慢一点，却因 RTO 到期被当作丢失而重传。
本方案也不例外，必须承认这个代价，并把它控制住。

**先明确：多余的重复包是安全的，只是浪费。**

- 客户端收到重复的 1 时，`expected` 已推进 → 按 `n < expected` **直接丢弃**（3.3.4），
  **不会造成数据错误**；
- 唯一代价是**浪费一个 ICMP 包位**。在 `WINDOW_MAX=5` 下，一个包位约占 20% 窗口，
  代价并不小，因此仍需抑制。

**能否撤销？能，且是自愈的。**
只要在 RTO 到期前，真实的分片 1 到达客户端：

1. 客户端把它交付、`expected` 跳到 2；
2. 下一次请求携带 `ack = 2`；
3. 服务端看到 ack 已覆盖 1 → **撤销对 1 的重传**（前提"ack 仍落后"已不成立）。

所以关键在 **RTO 要大于"最大乱序延迟"**：

```
SRTT   = 平滑 RTT 估计
RTTVAR = RTT 偏差估计
RTO    = SRTT + 4 × RTTVAR        # 与 TCP 同款，适应抖动
RTO    = max(RTO, RTO_MIN)        # 下限（建议 1s），抑制对抖动的过度反应
```

采用自适应 RTO 后，只有当延迟噪声超过约 4 倍标准差时才会误判，概率显著降低。

#### 5.4.6 降低误判的三个层次（建议）

| 层次 | 做法 | 效果 |
| --- | --- | --- |
| **必做** | 自适应 RTO（`SRTT + 4×RTTVAR`，带 `RTO_MIN` 下限） | 大幅降低误判率 |
| **建议** | `ack` 附带**接收位图**（SACK 式） | 服务端精确知道"只缺第 1 片"，避免补错片 |
| **可选** | 依据"`ack` 是否停滞"动态调整 RTO | 停滞时才激进补，否则保守 |

**`ack` 位图的价值**：若 `ack` 只带连续号，服务端只知道"1 未确认"，但不知道
客户端是否已收到 2~5。附带位图后可表达为 `ack=0 + 已收{2,3,4,5}`，于是：

- 服务端**明确**只缺 1，补洞精确，不会误补 2~5；
- 也能辅助判断：若位图显示"后续分片持续到达"，说明链路在动，1 更可能是**延迟**而非丢失，
  此时可保持保守、不急着补。

**判据（简化版）**：

| 观测 | 推断 | 动作 |
| --- | --- | --- |
| `ack` 停滞，无明显后续到达 | 大概率真丢 | RTO 到期即补 |
| `ack` 停滞，但位图显示后续分片持续到达 | 疑似延迟（前面那片在慢） | 可再等，避免无谓重传 |
| `ack` 正常前进，偶有超前片 | 链路通畅 | 不动 |

> 无论采用哪一层次，"`ack` 落后 + RTO 过期"这两个条件都必须同时满足才补发（5.4.2）；
> 上述优化只是让**裁决更准**，不改变"重复包安全、客户端丢弃"这一兜底保证。

#### 5.4.7 辨析：延迟确认（delayed ACK）能解决误判重传吗

**不能。方向相反。**

TCP 的延迟确认（delayed ACK）目的是**合并确认、减少包数**（捎带确认，最多等约 200ms）。
放在本方案里：

| | 改动的是 | 对本问题（1 慢却被重传）的影响 |
| --- | --- | --- |
| 延迟确认 | 接收方**报告 ack 的时机** | ❌ 让 ack 报得更晚，**加剧**误判 |
| 延迟重传（`RTO`） | 发送方**判定丢失的时机** | ✅ 直接对症 |
| `ack` 位图（5.4.6） | 发送方**对缺口认知的精度** | ✅ 直接对症 |

**根因分析**：本问题的症结在**接收侧的保守性不足**（服务端按 `发出时刻 + RTO` 判丢，
不管客户端何时报 ack），而非**发送侧的报告及时性**。因此：

- 服务端判丢**与"客户端何时发 ack"无关**；
- 若客户端因延迟确认而报得更晚，服务端看到 `ack` 落后的时间**更长**，
  命中 `RTO` 过期的人数更多 → **误判率上升**。

所以用延迟确认去解决误判重传，是在错误的方向上增加延迟。

**延迟确认在本方案里仍然有价值，但目标是另外两个**（须与 4.2 的低延迟目标权衡）：

1. **减少上行请求数**：把"取下行"的请求攒批发送，降低 ICMP 包数（对抗限速很有意义）；
2. **配合位图**：攒批后一次携带更新的接收位图，信息量更大、开销更省。

⚠️ **与 4.2 的冲突**：4.2 要求"常驻维持 ≥1 个在途请求"以拉取下行。
若延迟确认使请求变少，下行延迟随之变大。因此：

- **不能简单加固定 `sleep`**；
- 二者需按场景取舍：**有待发/待拉内容时立即发**，仅在"确实无事"时才攒批；
- 等价于：延迟确认只应用于**纯粹的空 pull**，不应用于承载数据或响应的请求。

### 5.5 无在途请求时的行为

若下行数据到达但此刻没有任何 pending 请求，数据留在下行队列中，
直到下一个请求进来才被派发。这是拉模型的固有行为，靠 4.2 的常驻拉取兜底，不是缺陷。

### 5.6 场景推演：下行乱序（丢首片）会卡死吗

**场景**：服务端依次把分片 1~5 塞进 5 个请求的回包发出，客户端**只收到 2、3、4、5，第 1 片丢失**。

正确的处理路径（不会卡）：

| 步骤 | 客户端 | 服务端 |
| --- | --- | --- |
| 1 | 重组区缓存 2~5，`expected=1`，**不交付** | — |
| 2 | 请求中携带 `ack = 0`（**连续**收到的最大号！） | — |
| 3 | — | 收到请求：按 `ack=0` 释放不了任何分片；发现第 1 片 RTO 过期 |
| 4 | — | 取**最早未确认**的第 1 片，用当前请求身份重发 |
| 5 | 收到 1 → 补齐 → `expected` 一次推进到 6，交付 1~5 | — |

到此链路恢复。**关键在步骤 2 的 ack 语义**：

- `ack` = **最大连续收到号**（= 0，正确）→ 服务端知道 1 丢了 → 补 1 → 恢复；
- `ack` = **收到过的最大号**（= 5，错误）→ 服务端以为 1~5 全部送达 →
  **永不补 1** → 客户端 `expected` 永远停在 1 → **真卡死**，
  且新分片 6、7… 持续被缓存不交付，**内存无限增长**。

> 因此 `ack` **必须是"最大连续号"语义**（3.2 已如此定义），
> 实现时若图省事写成 `max(收到的序号)`，会在丢首片时静默死锁 —— 且症状是"小概率卡住"，极难复现定位。

#### 5.6.0 补洞是"事件的"，不是"超时的"

上表中步骤 2~5 的响应粒度是**几个 RTT**，而不是等 `T`（数秒）超时：

- 客户端一收到超前分片（如收到 2 而 `expected=1`），**立即**发一个请求并携带 `ack=0`
  （**不等**任何计时器，见 5.6.2）；
- 服务端收到后**立即**获知"第 1 片未被确认"，无需等待；
- 于是补洞的触发是**事件驱动**的：一次 ack 反馈 + 一次补发。

**职责划分（关键）**：

| 机制 | 时机 | 作用 |
| --- | --- | --- |
| `ack` 反馈 | **立刻**（发现缺口即拉取） | 让服务端**知道**丢了哪片 |
| `RTO` 过期 | 分片发出后 ≥ RTO 仍未被确认 | 让服务端**决定**何时补发 |

一句话：**`ack` 负责"告知"，`RTO` 负责"裁决"**。

- 少了 ack 反馈 → 服务端不知道缺口位置，只能盲等；
- 少了 RTO 裁决 → 服务端会把"ack 只是还在路上"误判为丢包，导致大量无谓重传
  （`WINDOW_MAX=5` 下每个 ICMP 包位都很贵，无谓重传会直接挤占有效带宽）。

> 注意：`ack` 落后本身**不是**重传依据，它只是"候选信号"。
> 服务端必须在 ack 落后 **且** 对应分片 RTO 过期时，才真正补发。

#### 5.6.1 两套序号体系绝不可混用

这个场景还会暴露一个更隐蔽的设计冲突：

| 序号 | 归属 | 语义 |
| --- | --- | --- |
| 上行 `msg_seq` | 客户端 → 服务端 | 客户端发来的第几片（用于**请求幂等**） |
| 下行分片序号 | 服务端 → 客户端 | 服务端发出的第几片（用于**补洞重组**） |

二者**完全独立**。若把"上行请求幂等"与"下行补洞"用同一张表/同一套索引来管理，会出现：

- 客户端重传的请求，其上行 `msg_seq` 恰好命中幂等表 → 服务端**重放上次的回应**（可能是第 3 片），
  而客户端此刻急需的是第 1 片 → **补洞被幂等逻辑劫持，永远补不上 → 卡死**。

**正确做法**（已在 5.2 / 5.3 落实）：

1. 幂等表按**上行 `msg_seq`** 索引，命中时只跳过**副作用**；
2. **补哪个下行分片**由下行缓冲的"最早未确认"决定，与幂等表无关；
3. 两者是不同分支，须保持固定优先级（幂等 > 补洞 > 新数据 > 纯 ACK），
   即 5.3 伪代码中的分支顺序。

#### 5.6.2 补洞的唯一驱动力是"客户端发请求"

服务端**不能主动发包**（1.2），所以补洞必须等客户端送来一个请求。

推论：**客户端一旦检测到缺口（`expected` < 已缓存最大号），必须尽快发新请求去拉，
而不能干等在途请求自然超时**。否则：

- 服务端没有新请求到达 → 不会补 1（哪怕它早知道 1 未确认）；
- 客户端 `expected` 停在 1 → 停滞可能长达一个完整的 `T`（数秒）。

因此 4.2 的拉取循环中，"存在缺口"应作为**立即发起请求的触发条件**，
优先级等同于"有待发数据"。

#### 5.6.3 缺口超出窗口容量的风险

`WINDOW_MAX=5` 时，若在途请求被大量占用而又恰好出现缺口，需保证
**补洞请求不会被"新数据请求"挤掉**。这与 5.6.2 同源：
缺口应提升请求优先级，而不是排在普通拉取之后。

## 6. 参数表

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| `T` 请求超时 | 数秒级（默认 10s） | 客户端 per-request 超时；由客户端在 CONNECT 中告知服务端 |
| `margin` | 0.5s | 服务端等待窗口 `W = T - margin`，留出回程时间 |
| `Δ` 派发间隔 | 0.05 ~ 0.1s | **必须 < margin** |
| `WINDOW` 在途请求数 | 空闲 1，传输时动态 1→5（见 6.1） | 决定下行吞吐上限与丢包检测能力 |
| 回包缓存 TTL | 60s | 需 > 最大重传总时长，否则幂等失效 |
| `RTO` 下行分片重传超时 | 自适应 `SRTT + 4×RTTVAR`，下限 `RTO_MIN≈1s` | 超时仍未被 ack 覆盖才判丢（见 5.4.2、5.4.5） |
| `MAX_RETRY` | 视 `T` 与总容忍时长而定 | 超过则判定链路失效 |
| 保活间隔 | 远小于 NAT conntrack 超时（常见 30~180s） | 空闲时也不能停止拉取 |
| `MSS` / 分片大小 | 受 MTU 约束 | 由 CONNECT 协商 |

### 6.1 窗口动态调整策略（空闲 1 / 上限 5）

策略：**空闲时 `WINDOW = 1`；有数据传输时窗口动态爬升，上限 `WINDOW_MAX = 5`。**

### 为什么压到 5（而不是按 BDP 取几百）

- ICMP 常被网络设备**限速（rate limit）甚至主动丢弃**，突发大量 ICMP 容易触发限速或异常检测；
- 空闲时 1 个在途请求就足以完成"保活 + 取下行"，维持更多纯属浪费；
- 小窗口把服务端的 pending 表、客户端的重组缓冲与内存占用压到极低。

### 状态与转换

| 状态 | 窗口 | 进入条件 |
| --- | --- | --- |
| 空闲 IDLE | 1 | 连续 N 个周期既无上行数据、回包也无载荷 |
| 传输 ACTIVE | 1 → 5 动态调整 | 有上行数据待发，或回包中带回下行载荷 |

爬升与退避（上限仅 5，无需完整慢启动/拥塞避免，用简化版即可）：

- **爬升**：每收到一个有效回包 `cwnd += 1`，直至 `WINDOW_MAX`；
  （因上限小，最多几个 RTT 即到顶）
- **退避**：发生超时重传即判定拥塞，`cwnd` 回落（建议 `max(1, cwnd/2)` 或直接回 1），
  再重新爬升；可记录 `ssthresh` 使二次爬升更保守；
- **回落到 IDLE**：ACTIVE 中连续若干周期无数据收发 → `cwnd = 1`。

### 由此确定的吞吐上限

\[
吞吐_{max} = \frac{WINDOW_{MAX} \times MSS}{RTT}
\]

以 `MSS=1200B` 计：

| RTT | 吞吐上限（`WINDOW_MAX=5`） |
| --- | --- |
| 50 ms | ~120 KB/s（≈ 1 Mbps） |
| 200 ms | ~30 KB/s（≈ 0.24 Mbps） |

即本方案定位为**低带宽、高可靠通道**（保活 / 小流量 / 轻量代理），不以吞吐为目标。
若确需更高吞吐，再调大 `WINDOW_MAX` —— 代价是 ICMP 限速风险与更大的缓冲开销，
参数应可配置以便按网络环境调整。

### 小窗口对丢包检测的影响

- 窗口上限 5 时，最多产生 4 个重复 ACK —— 快速重传（阈值通常 3）**勉强可用但收益有限**；
- 因此**丢包主要仍靠 per-request 超时发现**，`T` 的取值对性能影响较大，不宜设得过大；
- IDLE 窗口为 1 的副作用：下行突发数据到达时，最初几个分片每个 RTT 只能带一个，
  随后窗口爬升才加速。可接受，因为爬升在数个 RTT 内即到顶。

### 连带约束

pending 表的兜底上限需 **> `WINDOW_MAX`** 并留重传/重排余量（建议数倍）。
`WINDOW_MAX=5` 的量级下该约束很容易满足。

## 7. 关键设计决策与取舍

### 7.1 为什么重传必须由客户端驱动

服务端无法主动发包（1.2），因此服务端"重传"只能搭下一次请求的便车。
而客户端可以随时发新包，天然拥有重传能力。把重传收敛到一端，避免双重重传与责任不清。

### 7.2 为什么 `msg_seq` 与 `icmp_seq` 必须分离

- `icmp_seq` 是**传输匹配键**（每重试都变），解决"这个回包属于哪次发送"；
- `msg_seq` 是**语义去重键**（重试不变），解决"这条消息是否已经处理过"。
  合二为一则无法同时表达这两层语义。

### 7.3 序号回绕

`msg_seq` 与 `icmp_seq` 均会回绕。所有基于序号的比较（去重、缓存命中、ack 推进）
必须**使用回绕安全的比较**，且缓存/去重条目需带时间戳，避免"回绕到同一序号"被误判为命中。

### 7.4 背压

下行队列无界会导致：上游推送快于客户端拉取时内存无限增长。
需要队列水位阈值，超过阈值时**暂停隧道读取侧**（等价于 TCP 零窗口），
由上层 TCP 自身的流控把压力传递到源端。

### 7.5 空闲保活与 NAT

即使无数据，也必须持续发空 pull：既是取下行数据的机会，也维持 NAT conntrack 条目。
保活间隔须远小于 conntrack 超时。

### 7.6 控制消息的特殊性

`CONNECT` / `RESET` / `CLOSE` 等控制消息**没有"拉取"语义**（对端不会为它们发请求），
因此不能依赖 pull 驱动重传。这类消息需要独立的重传/重试策略（例如发送方按计数重试若干次）。
实施时要明确区分"数据面（pull 驱动）"与"控制面（主动重试）"。

### 7.7 协议版本与兼容

本模型与"服务端主动推送/共享响应槽"的旧模型**协议不兼容**，混跑会静默死锁。
必须在包头携带版本/模式字段，握手时不匹配则**快速失败**并给出明确错误，而非降级静默。

### 7.8 生命周期与异常安全

- 派发协程随 session 启停，取消时必须清理 pending 表；
- 派发协程体需整体异常兜底：一旦它死亡，所有 pending 请求永远等不到回包 →
  客户端超时重传 → 服务端已无记录 → 当作全新请求重新处理 → **重复副作用**；
  因此异常时应主动 RESET 或重启派发器，而不是让它静默退出；
- session 关闭时，pending 中的请求应被妥善处理（发 RESET 或直接丢弃），不留悬挂状态。

### 7.9 顺序交付

链路可能乱序，客户端需按 `msg_seq` 顺序交付上层：缓存超前分片，等待缺口补齐；
缺口长时间未补齐则按累计 ack 触发对端 pull 驱动重传（5.4）。
具体算法（缓冲区、推进方式、上限）见 3.3.4 —— **顺序交付与分片重组是同一件事**，
因此重组逻辑应实现一次、双向复用。

## 8. 验收要点

- 高丢包 / 高抖动弱网下，大文件双向传输无丢失、无重复、无错序；
- 空闲连接下行延迟约等于一个拉取周期（应远小于秒级）；
- 强制杀掉任一端后，另一端不泄漏状态；
- 新旧版本混跑时快速失败，不静默死锁；
- 长时间空闲后连接仍可用（NAT 未超时）；
- 上游推送快于下行时内存有界（背压生效）；
- 单分片丢失时仅重传该分片（缺口补齐），不需重传后续已收分片；
- 因乱序误判而到达的重复分片被静默丢弃：不产生数据错误、不触发额外重传、不干扰 `expected`；
- 刻意让前一片延迟超过 RTO 时，重传发生但连接仍正确（自愈），且无数据重复；
- 乱序到达的分片不触发无谓重传，也不造成上层数据重复或错序；
- 异常对端发送超前 `msg_seq` 时重组内存不失控。
